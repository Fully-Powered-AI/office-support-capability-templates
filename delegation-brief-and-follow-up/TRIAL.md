# Delegation brief and follow-up: one trial on the invented example

- **Product:** Claude, run in Claude Code

Model: Sonnet 5.5 (model ID claude-sonnet-5-5), run as a subagent of a workflow script. It did not write the template.

Date: 2026-11-10

The inputs were the invented example in `public/example.md` (Tarnwick Advisory, Marta, Theo, Jonas and the others). No client data was used. The two parts of the example were run in turn: a brief written on the example's Monday 9 November 2026, and the weekly list for its Friday 13 November 2026. The run date above is the real date of the trial; the dates inside the output are the example's invented dates.

## Inputs used

By reference, from `public/example.md`:

- Part 1: the settings, and Marta's note to Jonas.
- Part 2: the settings, the delegation list (D-008 to D-016), the three updates, and the approved brief for D-014.

The assistant followed the fenced instruction block and the output format in `member/template.md`. It read the example's output only after producing its own. The example's inputs for Part 2 were read before Part 1 was written, so the list line for D-014 was written knowing the list's wording.

## What was observed

- Every part the format asks for was produced, and the fenced instruction block was enough to produce it. Nothing in either run hit a stop condition (the date was given, every header matched, no id repeated, nobody was asked to send, choose or rate anything).
- Compared with the published example, the substance is the same: the same due date and time, check-in dates, groups, working-day counts, three questions, three notes and the same two status changes. The checklist's date and count checks (items 3, 4 and 6) all held against the calendar.
- Differences from the published example:
  - Done means. The example puts "the main themes, how many clients raised each one, and three or four short quotes" under Done means. This run put them under What and wrote "not stated: Marta will check it against What and Format". The note does not say "done means", so the template allows either.
  - The PLX question. The example files it under Format; this run files it under What, as "the work in the PLX layout". The template does not say which field a layout belongs to.
  - The wording of the PLX question, the notes and the "To settle" facts differs slightly. The notes carry the same asks and dates.
  - List changes. The example lists five items, including conditional ones (D-010 "as Marta decides", D-011 moving the due date, and D-012 closing), each marked with the question it waits on. This run listed only the changes that rest on supplied updates and added one line saying the rest wait. The template says each change is listed "with the question it waits on, if any", which can be read either way.
  - The due time. The example writes "12:00 noon"; this run wrote "12:00". The template says to copy a time as written; the note says "noon".
  - The example's D-014 change has no last_update; this run also had none, because the template names only `acknowledged_on` and the status for that change.
- Facts not in the inputs. In this run's output: none found. The D-014 list line's title ("Summarise the autumn client feedback survey for the partners' planning day") is taken from the Part 2 list, not from Marta's note, which gives no list title. In the published example's output: the title of each brief and list line is the only wording not in the note. Outside the output, the example's closing prose says Marta answered that Jonas uses the PLX layout for every client report, and that Theo took the questions to Marta that afternoon; neither is in the inputs, which say only that the brief carries "Marta's answer on the PLX layout".
- Where the instructions were ambiguous and a guess was needed:
  1. The note says "Jonas can be slow to get going, so keep a close eye on him." The remark rule covers comments on a person's habits, so it was left out and the one-line notice printed. The template does not say what to do with the request for closer watching. This run added no extra check-ins and did not mention it beyond the notice.
  2. Handed-over date. The note gives none. This run took today's date, which the template implies but does not state.
  3. Which field a layout or content list belongs in (above), and whether "Done means" should hold the content the note lists.
  4. Whether a list-line task title may be reused from elsewhere. The template does not say where the title comes from.
  5. Whether "List changes" includes conditional changes (above), and whether a number counts lines or delegations.
  6. Where a Delivered date goes. The template says "Delivered, with the date they give" but not which field records it; this run used `last_update` and `last_update_on`.
  7. Sam's message says "Sent you". The template does not ask who "you" is, and the run did not either.
  8. D-010 had a check-in date (4 November) with no update behind it and no later update. The template does not say to raise that, so it is not mentioned, though the escalation question covers the task.
  9. "The planning-day pack" is an in-house name the note does not explain. The template's rule flagged only PLX; this run judged "pack" ordinary English. Another reader could flag it.
- The output follows the format closely, and the template is long; a model that skimmed it could miss the rule that a check-in date inside the look-ahead gets a note even for a task grouped as On track.
- This was one run, by one model, on an invented example. It does not show how the template works on a real note or list, or in another product.

## Edits made after this run

The template and the example were revised on 10 November 2026, after this run and after an independent review. These edits have not been run again. Each one settles a point listed above; none changes a date, a count, a group, a question or a note on the example.

- Handed-over date (point 2). The procedure and the pasted instructions now say it is today's date unless the note gives another. This run already took today's date.
- Done means and Format (point 3). The procedure and the pasted instructions now say that contents the note says the deliverable must hold go in Done means, that What names the deliverable itself, and that a layout, template or house style goes in Format. The published example already did this. This run put the contents under What, wrote "not stated" under Done means and filed the PLX question under What; the revised wording points to the example's choice.
- Title and task text (point 4). The procedure and the pasted instructions now say the brief's short title names the deliverable in a few of the note's words, and the list line's task starts with a verb and says, in the note's words, what the person will do and for what.
- List changes (point 5). The procedure and the pasted instructions now say that changes depending on the manager's answer are listed with the question they wait on, reading "as [manager] decides" where the answer is a choice, and that the count is of lines. The published example already did this, with five lines. This run listed two lines and a note; the revised wording points to the example's five.
- Delivered date (point 6). The procedure and the pasted instructions now name the fields: a short account of what the person said as last_update and the date they give as last_update_on. This run already used those fields.
- Closer watching (point 1). The procedure and the pasted instructions now say a request in the note to watch the person more closely adds no check-ins unless the manager gives their dates. This run already added none.
- The "(proposed)" mark. The procedure no longer says every proposed change is marked "(proposed)" wherever it is used; it now says every proposed change is listed under "List changes, once approved", and that the Delivered line marks its date "(proposed)". This run and the example already did exactly that.
- A moved due date. The pasted instructions now also carry the procedure's rule that an agreed new date sets due and records "Due moved from [old] to [new], set by [manager]" as last_update. The example's D-011 change line already reads that way.
- The due time. The procedure and the pasted instructions now say a time is written on the 24-hour clock, so "noon" is 12:00, and the example's two "12:00 noon" now read "12:00", as this run wrote them.
- Two long lines in the pasted instructions were rewrapped, and the acceptance-test note now says the tests have not been run as tests and that this run met cases like tests 6, 7, 10, 11 and 12.

Points 7, 8 and 9 above are unchanged. No recorded output or observation above was changed.
